# 历史日志配置说明

KubeDoor 的 AI 助手可以查询保存在 ClickHouse、Elasticsearch 里的历史日志，例如入口 nginx、Istio 网关、API 网关的访问日志，以及各个服务的应用日志和异常栈。用来排查「昨天下午某个接口为什么一直报 502」「这个请求经过了哪些服务、断在哪一层」「最近一小时有哪几类报错」这类问题。AI 自带的 Pod 日志只能看到容器当前的标准输出，Pod 重启或删除后就看不到了。

历史日志在 **系统管理 → 历史日志** 中配置，只有系统管理员能修改。配置保存在 PostgreSQL，保存后立即生效。对某个集群有只读及以上权限的账号，都可以让 AI 查这个集群的日志（网页 AI、企微 AI、外部 MCP 规则相同）。日志内容会作为对话上下文发给模型服务商。

## 几个概念

| 概念 | 含义 |
|---|---|
| 连接 | 一个 ClickHouse（HTTP 接口）或 Elasticsearch 的地址和账号。可以登记多个 |
| 日志源 | 一类结构和含义相同的日志，例如「入口网关访问日志」「Java 应用日志」。在这里填时间字段、正文、级别、Pod、状态码、耗时等字段对应哪一列，以及给 AI 看的用途说明和字段说明 |
| 集群绑定 | 某个集群的这类日志在哪张表 / 哪个索引、按什么条件过滤出属于这个集群的数据。不同集群可以绑到不同的表（一个集群一张表），也可以绑到同一张表再按字段过滤（例如 `env ∈ {prod-a}`） |
| 集群说明 | 每个集群一段文字，例如「这个集群没有接入 nginx 日志」「测试环境的应用日志只保留 7 天」 |
| 关联字段 | 能把同一个请求在不同日志里串起来的 ID，例如链路 ID、网关生成的请求 ID。可以是单独的一列，也可以写在正文里（例如 `TID:{value}`） |
| 网络架构说明 | 一段文字，告诉 AI 请求从哪里进来、经过哪几层、每层对应哪个日志源 |

AI 只能查当前集群绑定了的日志源。每次查询都会自动带上绑定的表 / 索引和过滤条件，AI 去不掉这些条件，也查不到别的表。

## 前提

| 项目 | 要求 |
|---|---|
| ClickHouse | 能访问 HTTP 接口（默认端口 8123）。集群部署时绑定**分布式表** |
| Elasticsearch | 7.10 及以上。AI 写原生 ES\|QL 需要 8.14 及以上，其余功能不依赖版本 |
| 网络 | KubeDoor 控制端（kubedoor-master）能访问上面的地址 |

### 建议使用只读账号

ClickHouse：

```sql
CREATE USER kubedoor_logs IDENTIFIED WITH sha256_password BY '<密码>'
  SETTINGS readonly = 2, max_execution_time = 60;
GRANT SELECT ON logs.* TO kubedoor_logs;          -- 换成日志所在的库，多个库各写一行
GRANT SELECT ON system.tables TO kubedoor_logs;
GRANT SELECT ON system.columns TO kubedoor_logs;
GRANT SELECT ON system.parts TO kubedoor_logs;     -- 扫描时统计行数和时间范围，可选
```

- `readonly = 2`：KubeDoor 每次查询会带上超时、读取行数上限等设置，`readonly = 1` 的账号不能带设置，这些限制就只能靠账号自己的配置。
- 集群部署时，分布式表对应的本地表也要授权（`GRANT SELECT ON logs.* … ON CLUSTER <集群名>`）。

Elasticsearch（Kibana 开发工具或 API）：

```json
POST /_security/role/kubedoor_logs
{
  "cluster": ["monitor"],
  "indices": [
    {"names": ["app-logs-*", "ingress-*"], "privileges": ["read", "view_index_metadata"]}
  ]
}
POST /_security/user/kubedoor_logs
{"password": "<密码>", "roles": ["kubedoor_logs"]}
```

`monitor` 用来读取版本号；`view_index_metadata` 用来读取字段列表。扫描时读取索引模板说明和保留策略需要 `manage_index_templates`、`read_ilm`，没有这两个权限扫描照样能用，只是不显示模板说明和保留天数。也可以用 API Key（认证方式选「API Key」，填 `id:api_key` 的 base64 编码）。

## 配置步骤

### 1. 添加连接

| 字段 | 如何填写 |
|---|---|
| 类型 / 地址 | ClickHouse 填 HTTP 地址，例如 `http://clickhouse.logging:8123`；Elasticsearch 填 `http://es.logging:9200`，前面有反向代理路径的带上路径 |
| 认证 | ClickHouse：用户名 + 密码；Elasticsearch：无 / 用户名密码 / API Key。密码加密保存，页面只显示「已保存」，编辑时留空表示沿用 |
| 超时 | 单次查询最长多少秒，ClickHouse 同时作为 `max_execution_time` |
| 并发 | 同一个连接同时进行的查询数，AI 按请求 ID 一次查多个日志源时用得上 |
| 单次扫描行数上限 | 仅 ClickHouse：每个分片最多读取多少行（`max_rows_to_read`），超过时查询会被拒绝，AI 会缩短时间或加条件再查。0 表示不限 |
| 允许原生查询 | 允许 AI 直接写 SQL / DSL / ES\|QL。关闭后 AI 只能用固定的几种查询 |

填好后点「测试」，页面会显示版本、账号是否只读等信息。

### 2. 智能配置：扫描 + AI 生成说明

点连接的「扫描」，KubeDoor 读取库表 / 索引的结构，再从每类日志里取几条样本：

- ClickHouse：列出分布式表（对应的本地表自动隐藏）和独立的 MergeTree 表，把字段完全相同的表归成一组。例如各集群的入口网关日志一集群一张表，结构一样，就归成一组；每个环境一个库、库里各有几种结构相同的表（例如网关日志和 web 访问日志）时，按表名分成几组。
- Elasticsearch：列出 data stream、别名和按日期滚动的索引（`app-2026.11.23` 归成 `app-*`），同样按字段归组。
- 每组显示行数、时间范围、保留天数（表的 TTL 或 ILM 策略）、字段、样本（已打码），以及低基数字段的常见取值（用来判断哪个字段区分集群）。

勾选要用的组，然后：

- **按规则生成**：按字段名猜出时间、正文、级别、状态码等字段，生成日志源和绑定草稿，不调用模型。绑定建议的规则：
  - 有区分集群的字段（例如 `env`）时，只建议取值和集群名或别名对得上的绑定，取值属于别的集群的不会放进条件。
  - 一个集群一张表 / 一个索引时，按名字打分：集群名里有区分度的词出现在表名里才建议；名字里 beta、test 这类环境词一边有一边没有会扣分；分不清是哪个集群的（例如所有集群共用的 nginx 表）不建议，需要手动绑定。
  - 关联字段只自动加入链路 ID、请求 ID、访问 ID 这类请求追踪 ID，优先用有索引的列，其次是正文写法。
- **AI 生成说明**：把扫描结果（样本已打码）交给企微专用模型，生成日志源的用途说明、字段说明、查询建议、关联字段、集群绑定建议和网络架构草稿。可以在「补充说明」里写已知信息，例如「请求 ID 由入口网关生成」「nginx 日志不区分集群」，生成得会更准。需要先在「系统管理 → 企微 AI 机器人」配置模型（机器人停用也能用）。

草稿逐项勾选后「应用到表单」，**检查、修改后再保存**。AI 推断的地方会标「（推断）」或「（待确认）」，数据里看不出来的事（某个 ID 由谁生成、两张表是什么关系）一定要人工确认。

### 3. 日志源

| 字段 | 说明 |
|---|---|
| ID / 名称 | ID 是 AI 调用时用的短名（小写字母、数字、`-`、`_`），保存后在绑定和关联里引用 |
| 类型 | 访问日志（有状态码、路径、耗时）/ 应用日志（有正文、级别）/ 其他 |
| 说明 | 给 AI 看：这类日志是什么、在请求链路里处于哪一层、哪些字段有什么规律、怎么查更快。**大表一定写上「按哪个字段过滤走索引、时间窗口不要太大」** |
| 时间字段 | 必填。ClickHouse 是 Date / DateTime / DateTime64 列，Elasticsearch 一般是 `@timestamp` |
| 语义字段 | 正文、级别、命名空间、Pod、服务、状态码、耗时、请求方法、路径、域名、客户端 IP 分别是哪一列，没有就留空。配了 Pod 字段，AI 才能按 Pod / Deployment 过滤、看某条日志前后的上下文 |
| 耗时单位 | 耗时字段的单位：毫秒、秒、微秒、纳秒 |
| 级别取值 | 「错误」「警告」等分别对应哪些值。不同语言的日志写法不一样，例如 Java 是 `ERROR`，Node.js 的 bunyan 是 `50`，Python 是 `ERROR` / `CRITICAL`，都填进「错误」，AI 查 `level=error` 时就能一起查到 |
| 关联字段 | 这类日志里有哪些请求 ID：选关联字段，再选「列」（填列名）或「正文写法」（例如 `TID:{value}`、`"traceId":"{value}"`，`{value}` 代表 ID 本身） |
| 字段说明 | 逐个字段写含义，AI 按字段过滤、分组前会看。扫描结果里的字段可以一键带出 |
| 默认返回字段 | AI 查明细时默认返回哪些字段，不填返回时间、语义字段和关联字段 |
| 打码 | 额外要打码的字段（整个值换成 `***`），以及正则（有捕获组只替换第一组）。常见的密码、令牌、Cookie、签名参数已内置打码 |

### 4. 集群

左边是 KubeDoor 已登记的集群。选一个集群：

- **集群说明**：这个集群的特殊情况，例如哪些日志没有接入、和其他集群共用哪些日志。
- **绑定**：点「添加绑定」，选日志源，再填：
  - 表 / 索引：ClickHouse 填 `库.表`（分布式表）；Elasticsearch 填索引、别名、data stream 或通配符（`app-logs-*`），多个用逗号分隔。
  - 过滤条件：这张表里属于这个集群的数据怎么筛，例如 `env ∈ {prod-a}`。一个集群一张表时不填。一张表包含多个集群、但没有字段能区分时（例如外部 nginx 同时转发给几个集群），也不填，在说明里写清楚。
  - 说明：例如「外部 nginx 不区分集群，含 prod-a、prod-b 的流量」。
- 点「预览」：用这个集群的绑定查最近 15 分钟的 5 条日志，并显示实际执行的查询，核对条件对不对。

在 KubeDoor 里改过名、已经删除的集群显示「未登记」，可以删掉它的配置。

### 5. 关联字段

| 字段 | 说明 |
|---|---|
| key / 名称 / 说明 | 例如 `trace_id` / 链路 ID / 「各服务日志里的 TID 和 Jaeger 的 traceID 相同」 |
| 取值格式 | 可选的正则，例如 `[0-9a-f]{32}`：用来校验 AI 传的值，也用来从正文里取出 ID |
| 链路 ID | 打开后，AI 从日志里拿到这个 ID 就可以接着用链路追踪查调用链（需要先配置「系统管理 → 链路追踪」） |

「验证」会从一个日志源里抽一些 ID，到其他日志源里查，显示命中了多少。命中率低说明这个 ID 并不是每一层都会打印，或者正文写法填得不对。

### 6. 网络架构说明

用几行文字告诉 AI 请求怎么走，写上每一层对应的日志源 ID，例如：

```markdown
- 外网请求：用户 → 外部 nginx（日志源 edge-nginx，不区分集群）→ 各集群 Istio 入口网关（ingress）→ 服务
- 浏览器的页面接口：入口网关 → BFF（日志源 bff，生成 request_id 往下传）→ 后端服务
- 服务之间的调用：经 API 网关（api-gateway，按路径第一段转发到服务）
- 应用日志：Java 服务在 app-java，Node.js 在 app-node；异常栈整条在一个文档里
- 排查 502 / 504：先看入口网关的 response_flags（UF/UH 是上游不可用、UT 是超时），再看上游服务那段时间的应用日志
```

## AI 怎么用

在 AI 助手里勾选 Skill「历史日志查询」（企微 AI 默认可用），然后直接提问，例如：

- 「prod-a 昨天 15:00~15:30 订单接口 502 是什么原因」
- 「最近一小时 order-service 有哪几类报错」
- 「这个 traceId 经过了哪些服务」

AI 会先读日志源和网络架构说明，再按需统计、查明细、归纳报错模式、按请求 ID 把各层日志串起来。日志里有链路 ID 时，接着用链路追踪看调用链。

## 常见问题

**AI 说这个集群没有某类日志**：在「集群」里给这个集群添加绑定。

**查询报「超出读取行数上限」**：时间窗口太大，或者条件没走索引。在日志源说明里写清楚大表该按哪些字段过滤（ClickHouse 看排序键，`SHOW CREATE TABLE` 里的 `ORDER BY`），AI 会照着做；也可以适当调大连接的「单次扫描行数上限」。

**AI 查到的日志不是这个集群的**：「预览」看实际执行的查询，检查绑定的过滤条件。

**Elasticsearch 按字段过滤查不到**：text 类型的字段只能做全文匹配，精确匹配需要 keyword 类型或 `.keyword` 子字段，在字段说明里写清楚哪些字段是 text。

**Elasticsearch 按某个字段过滤或关联很慢、超时**：索引映射设置了 `dynamic: runtime` 时，没有在映射里登记的字段都是运行时字段，没有索引，按它查要逐条计算。页面上的字段列表、扫描结果和 AI 看到的字段表都会标出「运行时字段」。关联字段优先用「正文写法」（例如 `"requestId":"{value}"`，正文 `message` 有全文索引，按 ID 查一般几十毫秒）；经常要过滤的字段，建议在索引模板里登记成 keyword。

**能不能限制只查某几个库表**：KubeDoor 只会查绑定了的表 / 索引。原生 SQL 必须用 `$src` 引用日志源，不能引用其他表、用表函数或改设置。要进一步限制，就给只读账号只授权这几个库表。
