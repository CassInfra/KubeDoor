# KubeDoor 网页安装向导设计

状态：首版已实现于 `src/kubedoor-setup` 和 Web 的 `/#/setup`，启动与使用见 [部署说明](../../deploy/README.md#网页向导安装推荐)。本文保留设计及验收约定；配套 [交互原型](designs/web-install-wizard.html) 仍为演示，不连接数据库、不创建 K8S 资源。首版管理员固定为 `kubedoor`，Agent 在控制端安装完成后单独接入；启动命令需使用含新功能的已构建镜像，安装机器只需单独的 `install.sh` 和可用的 `kubectl`。

## 目标体验

新用户只启动一个 Web 安装入口，打开浏览器，完成 **5 步**即可使用控制台。PostgreSQL、VictoriaMetrics 由用户提供，沿用现有独立部署方式。首次安装不再要求编辑 `kubedoor.conf`，不展示环境变量名或大段 JSON。

首次安装入口：

单独取得 `deploy/install.sh` 后执行：

```sh
sh install.sh
# 也支持：bash install.sh
```

脚本兼容 POSIX `sh` 和 `bash`，通过内嵌 YAML 与 `kubectl apply` 启动 Web、setup 及必要权限。setup 在集群内生成安装密钥，脚本读取并打印实际 Web 地址和密钥。安装机器不需要 Python、jq、独立配置文件或完整源码。命名空间默认 `kubedoor`；镜像仓库、版本和第三方镜像放在脚本顶部，可用参数覆盖。运行时模板和看板随安装服务镜像发布，用户无需编辑。

首版专注于将控制端装到 **Web 所在 K8S 集群与命名空间**，自动识别部署身份，不额外要求上传控制端 kubeconfig。其他业务集群在安装完成后由已有的 Agent 安装页面接入。旧配置式入口保留在 `tools/legacy-install/`，继续供已有部署维护使用。

## 五步流程

| 步骤 | 用户看到和填写的内容 | 系统负责的事情 |
| --- | --- | --- |
| 1. 欢迎与环境检查 | 核对部署位置；用启动时生成的安装密钥进入 | 检测 K8S 访问、部署权限、节点架构、版本、同名资源和安装状态 |
| 2. 连接 PostgreSQL | 数据库地址、库名、用户名、密码；端口预填 5432 | 验证真实连接、身份认证、查询、目标 schema 建表权限、已有数据状态 |
| 3. 连接时序库 | 默认单机 VM；填写地址和认证；核对集群指标标签名 | 检查查询 API，生成单机写入地址，解释空库与标签检测结果 |
| 4. 设置管理员与访问地址 | 设置管理员密码，确认所有 Agent 能访问的 KubeDoor 地址 | 预填账号和入口，生成内部密钥及服务凭据，显示推荐组件组合 |
| 5. 自动安装 | 核对简洁摘要，点击“开始安装”；查看每项服务的实时状态 | 部署控制端、初始化表结构、逐项检查就绪与连接；全部通过后切换正式控制台并通知成功 |

第五步包含“确认 → 执行 → 完成”三个页面状态，不增加第六步。第一步主要是自动检查，真正集中填写信息的是第 2～4 步。

### 1. 欢迎与环境检查

- 主标题：“欢迎使用 KubeDoor”；说明“连接数据库和监控服务，即可开始管理集群”。
- 显示当前集群可核对的 API 地址或标识、命名空间、发布版本。集群标识来自可信部署信息，不伪造 in-cluster 环境中不存在的 kubeconfig context 名。
- 普通页面不展示 K8S 权限明细，只展示“可部署 / 无权限”，展开详情才能查看缺少的权限和修复办法。
- 无可调度的受支持架构节点是阻断项；暂时没有 metrics-server 是后续 Agent 接入提示，不阻断控制端安装。
- 检测出已有安装时显示“打开控制台”或“恢复安装”，不能覆盖初始化；发现同名但不属于本安装的资源时停止并说明冲突。
- 一次性密钥用于保护尚未创建管理员的入口。可通过启动脚本生成的短期访问方式兑换安装会话，密钥不进入查询参数、访问日志或长期浏览器存储。已有安装会话不反复要求输入。

### 2. 连接 PostgreSQL

常用表单：地址、数据库名（默认 `kubedoor`）、用户名（默认 `kubedoor`）、密码。端口、TLS 模式放在“连接选项”中；连接检查与最终组件使用同一套 TLS 设置。首版使用系统信任的证书，暂不提供自定义 CA 上传。

首版通过普通表单填写连接信息，口令始终脱敏；连接串粘贴解析作为后续增强。没有数据库时，可查阅现有 `postgres/` 独立部署说明，不把安装数据库变成主流程的必做子任务。

“测试并继续”从集群内执行，依次展示：

1. 地址和端口可以访问。
2. 账号可以登录指定数据库。
3. 查询可执行，目标 schema 可用。
4. 账号具备安装需要的建表和读写权限。
5. 数据库为空、属于本次未完成安装，或包含已有 KubeDoor 数据。

建表权限检查可在事务内使用唯一名称创建探测表并执行读写，随后回滚；此时不初始化正式业务表。不要求超级用户或建库权限。数据库不存在时明确提示先创建指定库。

错误贴在相关字段附近，例如“密码验证失败”“数据库 kubedoor 不存在”“可以连接，但没有 public schema 建表权限”，技术异常放入可展开详情。检测期间保留当前页面，不先跳下一步再报错。

发现已有 KubeDoor 数据，首版阻止当作全新安装：引导回已有控制台或受支持的恢复流程，不重置账号。跨环境恢复还必须验证原加密密钥等材料，不能新生成密钥后直接接管原库。

### 3. 连接时序库

默认类型为“VictoriaMetrics 单机版”，常用输入仅为服务地址、认证方式及对应凭据。地址与账号密码分开填写，系统处理编码和认证。VM Cluster、Prometheus 放入“使用其他监控服务”分支。

以 `http://192.0.2.20:8428` 为例：

| 用途 | 生成规则 |
| --- | --- |
| 控制端查询 VM | 使用上述基础地址调用查询 API |
| 控制端写入 VM | 自动生成 `http://192.0.2.20:8428/api/v1/write` |
| Agent 写入指标 | 使用第 4 步的 KubeDoor 对外地址加 `/agent/metrics/write` |

只有确认使用单机 VM 的标准路径时才自动生成其写入地址；有反向代理前缀时保留前缀。VM Cluster 需要区分查询、写入入口及租户，Prometheus 需要检查是否启用 remote-write receiver，不能统一靠拼接路径推断。上述分支显示必要的查询/写入参数。

**“集群指标标签名”放在本步骤常用区，明确标注重要，不折叠到高级设置。**

推荐页面说明：

> KubeDoor 用这个标签识别指标属于哪个集群。新部署保持 `origin_prometheus`；接入已有监控时，填写现有指标中区分集群的标签名，例如 `cluster`。
>
> 例如 `origin_prometheus="prod-k8s"`：这里填写 `origin_prometheus`，接入 Agent 时的集群标识填写 `prod-k8s`。新安装的 Agent 自动沿用这里的标签名。

可以根据已有的代表性 K8S 指标推荐标签，但不能无提示替换用户选择。不存在数据时显示“连接成功，尚未发现集群指标；接入 Agent 后自动出现”。存在数据但标签不匹配时指出问题，避免用笼统“连接成功”掩盖后续查不到集群的原因。

本步验证真实查询 API 和返回结构，不只测试端口或 `/health`。不能以查询成功、GET 写入路径返回 405，推定写入成功。默认完整采集模式在第 5 步验证真实写入；已有监控链路可以选择“仅查询，复用已有采集”，后续 Agent 安装默认仅装 Agent，并说明指标仍需有正确集群标签。

### 4. 设置管理员与访问地址

- 首版管理员账号固定为 `kubedoor`，用户只需设置密码并确认。使用正式认证模块的密码规则，首次设定的正式密码不再触发一次重复改密。
- “KubeDoor 访问地址”根据浏览器来源预填，结合启动服务信息给出可用建议，用户确认。不能把未经校验的 Host/X-Forwarded-* 当可信部署配置。
- `localhost`、`127.0.0.1`、临时端口转发地址标为“仅当前机器可访问”。允许通过本地转发操作安装页，但要求另填稳定入口供 Agent 连接。域名/Ingress 已存在时填其实际地址，不把证书和域名部署再扩成一套必填向导。
- 主区域显示推荐组件摘要。Grafana、告警组件等在折叠的“安装选项”中调整；不让用户逐项决定镜像、端口、资源限制。
- AI 服务使用默认部署，但模型、API Key、通知渠道、LDAP、镜像管理等均在安装后的对应页面配置，不阻塞首次安装。
- 内部通信 token、加密密钥、服务专用凭据自动生成并持久化；不要求用户理解或编辑 `kubedoor.conf.ai-secrets`。

### 5. 自动安装

先展示摘要：安装位置、数据库地址与库名、时序库类型与地址、集群标签、Web 入口、将安装的组件。口令与 token 不进入摘要。点击一次“开始安装”，创建持久化任务；此后刷新、关闭浏览器均不取消任务。

进度采用真实阶段与结果，不使用按时间增长的虚假百分比：

1. 复查连接和配置版本，保存运行配置及密钥。
2. 初始化数据库结构、管理员及内部账号；标识本次安装，防止重复初始化。
3. 部署 master、AI、告警及选定组件，等待实际就绪。
4. 检查各组件到 PG/VM 的连接；切换 Web 正式代理并确认可访问。
5. 验证登录链路和指标网关，记录安装完成，关闭初始化写入口。

#### 每项服务都有独立状态

安装页同时显示总体进度和固定的服务清单，每行包含“服务名称、当前状态、检查说明、耗时、查看详情”。部署过程中更新原行，不将多个服务合成一句“正在部署其他服务”。已完成的行继续保留，便于定位尚未完成的服务。

| 服务 | 页面展示与成功条件 |
| --- | --- |
| KubeDoor Web | 先显示“引导入口已就绪”，切换正式配置后验证控制台、登录代理和所选服务的代理入口 |
| kubedoor-master | 本次版本副本就绪，数据库结构初始化完成，认证与服务接口可用 |
| kubedoor-ai | 本次版本副本就绪，所需数据库初始化和内部接口检查通过；模型/API Key 可稍后配置，不以真实模型调用为安装成功条件 |
| kubedoor-alarm | 本次版本副本就绪，配置加载、数据库连接和服务接口检查通过；未配置通知渠道显示后续配置提示，不发送测试消息 |
| Grafana | 选中时验证副本就绪、服务健康、数据源连接与通过 Web 的访问；未选中显示“未选择” |
| vmalert | 选中时验证副本就绪、规则配置加载及所需数据源/通知端点连接；没有触发真实告警不代表失败 |
| Alertmanager | 选中时验证副本就绪、配置加载和服务就绪接口；未选中显示“未选择” |
| 当前集群 Agent（若选择一起安装） | 单独显示部署、向 master 注册和心跳验证；采集被选中时，vmagent、kube-state-metrics、node-exporter 各有独立状态行 |
| PostgreSQL（外部依赖） | 显示“连接验证通过”或具体连接错误，不显示成由本向导部署成功 |
| VictoriaMetrics / Prometheus（外部依赖） | 显示查询及所选模式需要的写入验证结果，不显示成由本向导部署成功 |

服务状态使用“等待部署 → 部署中 → 拉取镜像 / 等待调度 / 启动中 → 健康检查中 → 已就绪”，按实际观测更新；另有“等待依赖”“失败”“超时”“未选择”。状态不强制经过每个中间值，例如命中镜像缓存时可能直接进入启动中。等待依赖时明确说明“等待 master 就绪”，不让用户误以为卡死。

失败行显示简短原因，如“镜像拉取失败”“节点资源不足”“数据库认证失败”；展开后查看该服务相关的 Pod 状态、事件及脱敏日志。没有实际结果时保持“检测中”，连接中断显示“状态暂不可用”，不能保留失效的全绿判断并继续宣布完成。

#### 全部验证通过，才通知安装成功

“已创建 Deployment”“kubectl apply 成功”或 Pod 处于 `Running` 均不足以判定服务安装成功。后端需要确认控制器已观测本次期望版本（`observedGeneration` 对应当前 generation）、本次配置对应的新副本达到期望数量并就绪，以及该服务要求的健康/依赖检查通过；不能把旧 ReplicaSet 中仍就绪的副本算成本次部署成功。DaemonSet 按符合调度条件的期望节点数检查，而非只看到一个 Pod 就绪就通过。

总体状态由后端持久化任务聚合，前端不按动画时间或计数器自行判定。只有同时满足以下条件，任务才转入“安装成功”：

1. 所有选定服务均已就绪，包含勾选的可选组件；“未选择”不进入成功分母。
2. 外部 PG、时序库及当前模式要求的查询/写入检查通过。
3. 正式 Web 入口、登录链路及所选服务代理复查通过，初始化写入口已关闭，完成标记已持久化。
4. 本次安装要求的临时服务停用、权限撤销等收尾检查完成，结果可从正式入口读取。

任意选定服务失败、超时或检查状态未知，总体显示“安装未完成”，不弹成功通知，不自动跳转。可选组件既然被选中，它的失败也必须明确处理，不能自动降级为“略过”并显示整套成功。若允许取消某可选组件，需由用户明确调整安装选择后重新核对依赖和总体结果。

安装成功通知仅在任务首次转入成功时显示；轮询、刷新或重新进入页面只恢复结果，不重复弹出。页面保留全部服务结果和总耗时，再提供后续入口。临时安装服务的缩容及权限收尾单独显示；若仍待清理，明确展示“服务已就绪，安装收尾待完成”，完成所有必须的收尾检查后才展示整体成功通知。

“重试失败项”复用成功的部署资源，对失败项及受影响的依赖链重新执行检查；宣布总体成功之前仍复查其他服务当前健康状态，防止旧结果掩盖新故障。普通失败不删除成功部署，也不重新初始化数据库或管理员。各服务状态随任务持久化，刷新和安装服务重启可恢复。

验证写入时，使用临时测试身份发送一条专用的 `kubedoor_install_probe` 指标并在查询端核对，展示“将写入少量安装检测指标”。指标仅携带安装标识，不包含凭据；测试身份用后撤销。使用有界等待适配采集可见性延迟，超时显示明确失败原因。查询模式不做该写入探测，也不显示“写入验证通过”。

安装完成卡片显示入口地址、管理员用户名、组件状态，两个主要动作：

- **接入第一个集群**：登录后进入现有 Agent 安装向导，上传 kubeconfig、填写集群标识；继承 Web 地址、指标标签和网关写入地址。
- **进入控制台**：可先查看系统、配置 AI 或通知，不强制立刻接入 Agent。

没有 Agent 时工作台展示明确空状态：“控制端已就绪，接入集群后即可查看资源与监控”。不要让用户把空白指标页理解为安装失败。

## 页面与交互约定

- 桌面使用左侧 5 步导航、右侧单一表单卡片；当前步骤突出，已完成项可返回。移动端改成顶部“第 N / 5 步”，表单单列。
- 浅色背景、克制渐变、清晰标题和短说明；每一步只保留一个主要按钮。
- 表单显示业务名称，环境变量只在“技术详情”中出现。默认值直接可用，可选设置收进对应的小面板。
- 第 2、3 步“测试并继续”，检测成功后展示结果再转到下一步；失败留在原页并聚焦相关错误，支持重新检测。
- 修改已验证的地址、凭据、TLS 或标签会使相应检查失效；安装前核对配置 revision，不能拿旧的成功状态启动新配置。
- 检测支持明确超时、重试与取消等待。取消等待不会被误表述为撤销已执行的安装。
- 不把凭据写入 URL、日志或浏览器 localStorage。已保存密码只显示“已保存”，恢复页面无需明文回填。
- 按组件展示镜像拉取、调度、启动探针等异常，并给出下一步操作；详细日志可展开，默认不铺满终端输出。
- 失败后保留已成功步骤，修正后继续；不自动清库，不删除已存在业务资源，不一键从头重新安装。

## 引导架构与配置归属

当前 Web 是 nginx 静态页面，完整代理配置依赖 master 等服务；master 又在启动时强制连接 PG。因此需要独立的轻量安装 API，不能仅增加 Vue 页面，也不能让现有 master 在缺 PG 时承担初始化接口。

建议同一次 Web 启动创建以下内部资源，用户只操作一个 Web 地址：

```text
浏览器
  └─ KubeDoor Web
       ├─ /#/setup：安装页面
       ├─ /setup-api/：临时安装服务 → K8S API / 外部 PG / 外部 VM
       └─ 安装完成后：正式控制台代理 → master / AI / 告警 / Grafana
```

- 临时安装服务采用独立 Deployment 和专用 ServiceAccount，不依赖 PG 就能运行。其权限限制在目标命名空间内所需资源；Web 不挂载此部署身份。首个业务 Agent 的集群级权限由后续 Agent 安装流程处理。
- 引导阶段 nginx 只需静态页和安装服务即可启动。正式服务不可用时仍能显示安装进度/故障页；不能因为静态解析不存在的 upstream 而无法启动。
- 复用现有 manifests、默认值和共享渲染逻辑。安装 API 接收结构化输入，不把用户值拼进 shell 或用 `source` 执行用户配置。
- 安装器内的预检不能代表所有工作负载网络都相同。最终在真实组件运行环境中复查，覆盖 NetworkPolicy、DNS、TLS、节点网络差异。
- 完成后先记录状态、切正式流量并验证，再通过受限的一次性收尾任务停用临时安装服务、撤销其部署权限和安装凭证。收尾失败显示待清理状态，可重试；不能重新放开初始化。

| 配置/状态 | 保存位置和原则 |
| --- | --- |
| PG 连接参数、密码；时序库认证；加密密钥 | K8S Secret，供各组件一致读取；PG 连接信息不能只存在 PG 自己里面 |
| 非敏感部署配置、选定组件、安装 ID、阶段与完成标记 | K8S ConfigMap；数据库断开仍能区分未安装、安装中、已安装 |
| 密码尚未入库的初始化材料 | 临时 Secret；正式账号初始化后清理明文，账号库仅保留认证模块生成的密码哈希 |
| 用户、权限、镜像规则、镜像凭据、AI 设置等业务配置 | 沿用 PostgreSQL；敏感值按现有加密约定保存 |
| 安装历史 | 安装期持久保存脱敏摘要，PG 就绪后可记录审计；任何日志都不含口令 |

K8S Secret 本身不等于数据库加密保险箱，访问依靠集群 RBAC，必要时启用集群静态加密；此要求不需要变成普通用户必填步骤。运行时配置以集群中已应用版本为准，业务设置以 PG 为准，不同时维护浏览器草稿、配置文件和数据库三套互相覆盖的值。

首次安装完成后，数据库或服务故障必须进入诊断/恢复状态，**绝不能通过“PG 连不上”判断尚未安装**。实例级任务锁、配置版本与资源归属标记防止双击、多个浏览器、服务重启重复执行初始化。

原脚本环境的数据库/镜像配置迁移逻辑继续用于旧部署；网页首版对旧实例显示已有状态，不自动运行全新安装。后续升级入口需要独立的版本兼容、备份和恢复设计。

## 落地范围与验收

首版覆盖：同集群 Web 引导、外部 PG、单机 VM 默认流程、保留其他已有监控接入选项、真实预检、后台安装与恢复、正式控制台切换、现有 Agent 向导衔接。Docker 单容器控制端、跨集群安装 master、在线升级/迁移、自动安装外部 PG/VM 不混入本轮首装流程。

开发可按依赖推进：引导 API 与持久状态 → 连接预检及配置渲染 → 向导页面与安装任务 → 完成后的代理切换与权限收尾。与现有脚本共享默认值和渲染，避免两套部署行为逐渐不一致。

完成开发后至少验证：

- 空环境无 PG 配置时，Web 安装页面能够单独打开；未获得安装会话不能进行探测或写配置。
- PG 密码错误、schema 无权限、库已存在数据，各自显示正确处理方式。
- VM 空库、认证失败、写入失败、标签不匹配，不会全部归为“连接失败”或误判安装成功。
- 刷新页面、安装服务重启、多浏览器并发和重复点击可恢复且不重复建号。
- 主服务受 NetworkPolicy 阻断时，不能只凭安装器预检成功显示全绿。
- 任意一个选定服务拉取镜像失败、未就绪或健康检查超时，都不能弹出整体成功通知；未选择的组件正确标记且不阻塞。
- Pod 为 `Running` 但未 Ready、只有旧版本副本就绪、服务就绪但依赖不可用时，分别显示真实状态并阻止误报完成。
- 重试失败服务保留其他部署结果，并重新检查依赖与总体健康；刷新、重复轮询不重复发出成功通知。
- 外部 PG/VM 使用连接状态，AI 未配置模型、告警未配置通知渠道使用后续配置提示，不与服务部署失败混淆。
- 完成后 PG 故障、Web 重启、安装服务已经停用，均不重新进入初始化。
- 接入首个 Agent 自动继承指标标签与写入网关，实际指标按该集群标识出现在控制台。
- 桌面与手机可完成全部步骤；敏感输入不出现在响应回显、日志和持久浏览器存储中。
